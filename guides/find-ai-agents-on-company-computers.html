How to find the AI agents running on your company's computers

A practical guide for IT teams. By Andrew Sterling, Founder, Cuff AI · November 26, 2026

A year ago, "AI at work" mostly meant a chat window in a browser. Now it often means an agent: a program that can read files, run commands, edit code and call other services on a person's computer. Tools like Claude Code, OpenAI Codex, Cursor, Gemini CLI and GitHub Copilot's agent features fall in this group, and staff often install them on their own because they are useful.

That is not a bad thing. But it means many IT teams can no longer answer a basic question: which AI agents are running on our computers, and what are they allowed to do? This guide covers how to answer it, starting with what you can do today with no new tools.

Why it matters now

Agents act with the permissions of the person who runs them. If a developer can read a folder, push code or reach a cloud account, an agent running on their laptop usually can too.

The tools themselves also have bugs, like any software. In October, researchers reported security flaws in the built-in browsers of five popular AI developer tools, and some were still unpatched when the news came out. When that happens, the first thing you need is a list of who has the affected tool installed, and which version. Without that list, you are guessing.

Canada's Cyber Centre made a related point in its October bulletin on agentic AI: the basics still apply. Know what you have, limit what it can reach, keep logs, and decide in advance who can shut something down.

Where to look on each computer

There is no single setting that lists every agent, so you have to check a few places. On a small number of machines you can do this by hand.

  • Installed applications. Look for desktop apps such as Cursor, Claude Desktop, ChatGPT Desktop and Windsurf in the Applications folder on Mac or in installed programs on Windows.
  • Command-line tools. Many agents are installed as terminal commands, often through npm, pip or Homebrew. Running npm list -g --depth=0 and brew list shows globally installed packages. Look for packages such as @anthropic-ai/claude-code, @openai/codex and @google/gemini-cli, and for commands such as claude, codex, gemini, aider or goose.
  • Editor extensions. VS Code and its forks support AI extensions. Run code --list-extensions or look in the extensions folder in the user's home directory.
  • Configuration files. Agents keep settings in hidden files and folders in the user's home directory (on Windows, C:\Users\<name>), such as .claude and .claude.json, .codex, .cursor, .gemini, or .codeium/windsurf. One of these is a strong sign the tool has been used, even if it is not running right now. Many also list the extra tools (MCP servers) the agent is allowed to call, which is worth reading.
  • Running processes. Activity Monitor on Mac or Task Manager on Windows will show agents that are running at the moment. This misses tools that are installed but idle.

Write down what you find for each machine: the tool, its version, and who uses it. Version matters, because security fixes come in updates.

Why doing this by hand does not scale

The manual approach works for five or ten computers. Past that, it breaks down quickly.

New tools appear every few months, and existing ones change names, install paths and config folders. A check you script today may miss next quarter's tool. People install and remove things between your checks. And a list tells you what exists, but it does not let you do anything about it. If a serious bug is announced on a Friday afternoon, a spreadsheet will not stop the affected agent on forty laptops.

Your existing tools help some. Device management and endpoint software can often report installed applications, and they are worth using. But most were not built to recognize AI agents specifically, and command-line tools installed in a user's home folder are easy to miss.

What to do once you have a list

  1. Decide on a policy. Which tools are approved? What should agents be allowed to do: read only, edit files, run commands? Write it down in one place and apply it to everyone, rather than leaving each person to configure their own tool.
  2. Make sure you can stop them. Know how you would shut down a given agent across the company if you had to, and who is allowed to make that call.
  3. Keep a record. When you change a policy or stop an agent, log it. If an auditor, client or insurer asks later, you want a record that shows whether it has been edited after the fact.
  4. Repeat. Treat this as an ongoing check, not a one-time project.
